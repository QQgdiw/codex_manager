# 下一步协作指南

本文档用于说明你接下来如何配合我推进项目。后续我编写的、需要供人类阅读的 Markdown 文档，默认使用简体中文。

## 当前项目状态

首期基础闭环和市场强化已经完成。当前已经有资源市场、白名单、审批辅助表、场景配置、部署 dry-run、静态验证、回滚记录和状态文件。

但还没有完成真实安装部署。当前部署入口仍是 planning-only，load verification 和 smoke verification 也还没有接入真实验证器。

## 下一步建议目标

下一阶段建议优先做一件事：接入真实部署适配器和真实验证器。

目标不是一次性安装所有工具，而是选择 1-2 个低风险、已批准的工具，跑通：

1. 读取白名单。
2. 生成部署计划。
3. 执行真实部署或确认本地已存在。
4. 运行静态验证。
5. 运行加载验证。
6. 运行最小功能调用验证。
7. 记录验证结果。
8. 失败时执行受管回滚或记录不可回滚残留。

## 你需要提供什么

如果你要我继续推进下一阶段，请直接告诉我：

```text
继续下一阶段：接入真实部署适配器和验证器。
优先选择风险最低的已批准工具。
```

如果你希望指定工具，也可以这样说：

```text
下一阶段先验证 browser 和 superpowers。
```

如果你希望先做审批调整，可以这样说：

```text
先根据 approval_review.md 调整白名单。
我批准/暂缓/拒绝以下工具：……
```

## 你不需要做什么

- 不需要手动整理项目结构。
- 不需要手动运行测试，除非你想自己复核。
- 不需要把凭据发给我；如果确实需要验证登录状态，我会只运行状态命令，不读取或输出 `auth.json` 正文。
- 不需要一次性决定所有工具，后续可以小批量批准、小批量部署、小批量验证。

## 推荐推进顺序

1. 先确认下一阶段范围：真实部署适配器和验证器。
2. 选择最小工具集合：优先已批准、低副作用、容易验证的工具。
3. 我编写实施计划并明确风险边界。
4. 你确认计划。
5. 我执行实现、测试、提交和推送。

## 重要边界

- 白名单批准不等于已经部署。
- 静态验证通过不等于工具可用。
- load/smoke 验证未完成前，不应宣称工具已经可用于生产工作流。
- 涉及联网、用户目录写入、系统级安装或潜在破坏性操作时，我会按权限要求申请授权。
