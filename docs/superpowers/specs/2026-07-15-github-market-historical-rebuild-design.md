# GitHub 市场历史重建设计

> **状态**：待用户审阅
>
> **编写日期**：2026-07-15
>
> **适用范围**：`Resources/github_market.md`，覆盖 2026-W01 至采集日所在周。

## 1. 背景与问题

当前 `github_market.md` 的 W01-W26 使用周度表格保存近似候选池，缺少新市场规范要求的 `github-record` 标记、统一中文字段和逐项风险说明。旧记录还包含股票投机、网文创作、视觉小说、模型微调和消费娱乐等与研发者工作明显无关的条目。只追加 W27-W29 会使历史部分继续违反当前收录规则，且无法让跨文档验证器建立完整来源关系。

本设计将 W01-W29 视为同一份可审计档案：所有历史候选均重新判断保留或排除，保留项采用统一结构重新编写。历史周的榜单证据无法完整回溯时，使用来源等级 C，并明确该记录是近似候选，不代表该周精确 Star 或 GitHub Trending 排名。

## 2. 目标与非目标

### 2.1 目标

- 重建 W01 至 W29 的研发相关 GitHub 候选档案，按最新周到最早周排列。
- 逐项复核全部历史候选，排除与研发者工作明显无关的项目。
- 每个保留项都有一个可解析的 `github-record` 标记，并具备中文说明、场景、输入、输出、部署条件、风险和保留理由。
- 同一规范化 `owner/name` 只保留一个主条目；不足 20 条的周如实记录，不降低 Star 门槛或引入无关项目补足数量。
- 使用 `github-market.mjs validate` 证明记录字段、跨周去重和派生关系满足硬约束。

### 2.2 非目标

- 不将 GitHub Search API 当前结果描述为历史 Trending 的精确快照。
- 不改变 `Resources/tool_whitelist.toml`、审批状态或任何部署行为。
- 不为历史记录虚构 README、许可证、安装命令、硬件兼容性或 Star 历史。
- 不把模型训练、模型微调、消费娱乐、股票投机、纯演示或只含宽泛 agent 关键词的项目作为研发候选收录。

## 3. 收录与来源规则

### 3.1 候选来源

- W01-W26 的初始候选来自当前文档已有周度表格；这是待审计输入，不是自动保留清单。
- W27-W29 的初始候选来自 `scripts/markets/github-market.mjs collect` 输出的公开 GitHub Search 数据。
- 所有候选必须在采集数据中满足 `stars >= 1000`。候选不够时保留不足，不放宽门槛。
- 当前公开 README、组织主页或仓库元数据只能补充当前功能、部署和风险，不能证明历史周排名或历史 Star 值。

### 3.2 来源等级

| 等级 | 含义 | 使用条件 |
| --- | --- | --- |
| A | 可验证的官方历史来源 | 有明确周次、官方或可验证历史材料时使用。 |
| B | 当前公开仓库 README 或官方文档已核验 | 只能证明当前功能与部署信息；历史周依据仍需单独说明。 |
| C | 近似回溯候选 | 只具备现有表格或 GitHub Search 公开元数据时使用，必须写明不完整性。 |

历史候选默认 C。只有在本次能读取公开 README 或官方文档、并且说明内容仅限当前事实时，功能与风险说明可附加 B 级依据；这不改变其历史周证据的近似性质。

### 3.3 逐项判断

保留项必须与嵌入式、硬件、机器人、ROS、AI 工程、研发自动化、工程文档处理、安全验收或通用软件研发流程存在具体关联。边界项目读取 README 或官方文档后判断。

以下类型默认排除：小说或网文生产、股票投机、视觉小说、消费娱乐、纯视觉演示、模型训练或微调、仅用于模型能力展示的仓库，以及没有明确研发用途的泛 agent 项目。安全工具仅在授权测试和风险边界明确时保留，且不得据此产生部署建议。

## 4. 目标文档结构

文档从 W29 到 W01 排列，每周有候选总数、保留数、排除数、跨周重复跳过数和候选不足说明。W29 必须标明“截至采集日的部分周数据”。

每个保留条目使用三级标题和一个紧邻的隐藏标记：

```markdown
### owner/name

<!-- github-record:{"week":"2026-W27","repository":"owner/name","stars":1234,"capturedAt":"2026-07-15T00:00:00.000Z","sourceLevel":"C"} -->

- 链接：...
- 采集时可见 Star：...
- 项目属性：...
- 周次依据：...
- 来源等级：...
- 核心功能：...
- 适用工作流：...
- 输入：...
- 输出：...
- 部署条件：...
- 主要风险：...
- 保留理由：...
```

`stars` 表示采集时可见数值，不得被描述为该周历史 Star 数。`capturedAt` 是本次重建的采集或审阅时间。表格、摘要和每周说明不得与标记中的仓库、周次或来源等级矛盾。

## 5. 重建流程

### 5.1 候选总账

从旧表格和 W27-W29 JSON 建立临时候选总账，保留原始周次、仓库、现有 Star、描述、分类和旧置信度。总账仅位于 `.tmp/market-audit/`，不作为正式交付物。

总账先按仓库名小写化去重。跨周重复时仅保留最早被确认的主条目，并在相应周摘要记录跳过原因；不把重复项计入该周 20-30 个候选规模。

### 5.2 三批语义审阅

- 批次一：W01-W10。
- 批次二：W11-W20。
- 批次三：W21-W29。

每批将候选拆分为互不重叠的审阅分片。每条记录必须得到“保留”或“排除”结论；保留项给出统一字段草稿，排除项给出简短原因。边界项必须提供公开 README 或官方材料依据，无法核验时降级为 C 或排除，不得补写猜测内容。

### 5.3 主代理合并

主代理仅合并已审阅的保留项，检查周次、仓库键、Star、来源等级和中文字段是否一致。任何未审阅、跨周重复、低于 Star 门槛或字段不完整的项不进入正式文档。

## 6. 验证与质量门禁

- 运行 `github-market.mjs validate --github Resources/github_market.md`，要求硬错误、跨周重复和派生缺失均为 0。
- 对每周抽样首条和末条；候选少于 5 条的周逐条复核。
- 验证所有标记中的 `stars >= 1000`、ISO 周次、ISO 时间戳、来源等级和仓库键。
- 扫描中文质量：保留项必须有核心功能、适用工作流、部署条件、主要风险和保留理由；禁止把当前 Star 写成历史事实。
- 运行 Node 市场脚本测试、市场脚本 Pester 测试和最终全量 Pester。完整 Pester 外层超时至少预留 300 秒。
- 对正式文档做敏感信息扫描，不得出现 token、API key、Cookie 或本地凭据路径。

## 7. 失败边界与恢复

- GitHub API 限流、网络失败、候选解析失败或审阅材料不完整时，不覆盖现有正式文档。
- 任何一批审阅发现错误时，只重做该批临时材料；未通过的内容不合并。
- `validate` 失败时保留上一版有效文档和临时审计证据，修复候选或字段后重新生成。
- 新文档只有在所有保留项、周摘要和硬验证同时通过后才原子替换旧文档并提交。

## 8. 风险与取舍

该方案的主要成本是逐项审阅规模，而不是 API 请求次数。它避免把已有 638 条粗粒度候选伪装成高可信目录，也避免为了每周数量而保留无关项目。代价是部分周会显著少于 20 条，历史来源大多只能为 C 级近似回溯；这些限制将作为文档事实保留。
