## 来源差异与限制

- `/plugins` UI：本次没有可用的程序化接口读取用户看到的 `/plugins` UI 177 项数据；因此本文不声称已复现 UI 的 177 项列表。
- CLI JSON：本环境的 CLI 能返回结构化 JSON，但 `available` 和 `marketplaces` 均为空；这说明 CLI 当前没有暴露远程市场目录，而不是证明市场为空。
- 本地缓存：只代表当前机器已经缓存或启用过的插件，适合做版本和 manifest 证据，不代表完整市场。
- GitHub 仓库：`openai/plugins.git` 提供更广的 manifest 覆盖；候选目录数量 `179` 与 UI 177 项不一致，原始递归 manifest 数 `181` 还包含测试夹具。它可能包含尚未在 UI 上架、已下架、分批可见或区域/账号策略不同的条目。
- Clone 命令的 PowerShell 日志包含 Git 进度 stderr 被包装为 `NativeCommandError` 的痕迹；后续 `git status` 与 `git rev-parse HEAD` 已验证工作树可用。该现象已作为命令证据限制记录。

## 审批建议

- `approve_now` 只保留给 `Resources/approval_review.toml` 已明确建议立即批准且本地白名单已有证据的插件：`plugin.openai-bundled.browser` 与 `plugin.openai-curated.superpowers`。
- `approve_later` 用于本地已缓存、用途明确但不属于最小闭环必需项的文档类插件：Documents、Presentations、Spreadsheets。
- GitHub-only 第三方插件统一视为 `needs_review`：即使 manifest 可读，也必须先验证安装来源、包完整性、权限、第三方账号授权、许可证和回滚策略。
- 不因为 GitHub 仓库出现某插件而修改 `Resources/tool_whitelist.toml`；审批动作必须进入 `approval_review.toml` 和 `tool_whitelist.toml` 的正式流程。

## 后续核验缺口

1. 需要可审计的 `/plugins` UI 或官方 API 才能确认用户看到的 177 项列表与 CLI/GitHub/local cache 的差异。
2. 对任何 `github_only` 条目，批准前需要做隔离安装或 dry-run，记录下载来源、版本锁定、完整包 hash、权限声明和卸载/回滚路径。
3. 对第三方 SaaS 插件，需要单独确认 OAuth/API token 权限、数据出境边界、日志脱敏和最小授权范围。
4. 对本地 runtime 插件，manifest hash 只能证明 `plugin.json` 内容；正式部署前仍应补齐完整目录或发布包 hash。
