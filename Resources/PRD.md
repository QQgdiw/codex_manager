# Codex 工具资源管理与自动部署项目需求文档

> **文档状态**：首期需求已确认
>
> **文档版本**：v1.0
>
> **编写日期**：2026-06-13
>
> **目标读者**：项目研发者本人
>
> **适用环境**：Windows、PowerShell、Codex

## 1. 文档目的

本文档用于明确 Codex 工具资源管理与自动部署项目的产品目标、首期范围、核心流程、交付物和质量边界，为后续项目计划、实现与维护提供统一依据。

本文档强调需求和产品边界，不规定所有实现细节，也不将验收标准拆解为逐条测试用例。

## 2. 项目背景

研发者主要从事嵌入式、硬件和机器人相关工作，关注飞行机器人、轮式机器人、导航、ROS、AI 及工程文档处理，具有 NVIDIA Jetson NX、RK3588、Zynq、STM32、RP2350 等平台的软件和硬件开发经验。

Codex 可通过 Plugins、MCP、Skills 及其他工具扩展能力，但目前存在以下问题：

- 工具来源分散，难以快速判断功能、适用场景和部署条件。
- 不同工具之间可能功能重复、互相冲突或与 Codex 原生能力重叠。
- 不同研发场景需要不同工具组合，手工维护配置容易遗漏或过度启用。
- 第三方工具的安装、验证、版本固定、凭据管理和失败回滚缺少统一流程。
- GitHub 热门项目和 AI 行业事件变化较快，需要可追溯、可增量维护的信息目录。

因此，需要建设一个面向个人研发者的工作区，在资源调研、工具选择、配置生成、自动部署和验证之间形成基础闭环。

## 3. 产品定位

本项目是一个面向个人研发者的 Codex 工具资源管理与部署工作区。

项目通过 Markdown 资源目录、TOML 白名单、场景化配置和 PowerShell 自动化流程，帮助研发者：

1. 了解值得关注的 Plugins、MCP、Skills、AI 工作流工具和行业事件。
2. 根据具体研发场景选择最小且充分的工具组合。
3. 在明确来源、版本、权限和风险后安装第三方工具。
4. 自动验证工具是否完成安装并具备最小可用能力。
5. 在失败时回滚受管范围内的变更，并保留可追溯记录。

## 4. 产品原则

### 4.1 最小充分集

配置生成优先使用 Codex 原生能力，其次使用官方 Plugin 或 Skill，再次考虑 MCP。相同或高度重叠的能力默认只启用一个，避免重复消耗、指令冲突和维护负担。

### 4.2 宽进严标

资源筛选只排除与研发者工作明显无关的项目。其余项目可以保留，但必须明确标注相关度、适用场景、成熟度、部署条件和风险，避免因筛选过严错失跨领域工具。

### 4.3 来源可追溯

资源条目必须记录官方仓库或公告链接、采集时间及数据来源。近似回溯数据还必须标注可信度和数据不完整性，禁止把推测描述为精确历史事实。

### 4.4 状态严格区分

系统必须区分以下状态，不得混用：

- 已收录
- 已建议进入白名单
- 已批准
- 已部署
- 已静态验证
- 已完成加载或启动验证
- 已完成最小功能调用
- 验证失败

### 4.5 安全优先

第三方代码只有在白名单批准后才允许自动部署。版本必须固定，凭据不得明文写入配置、日志或版本库，安装失败不得静默忽略。

### 4.6 增量维护

市场文档采用增量更新并保留历史的方式。失效、归档或不再推荐的项目应标注状态和原因，不直接删除已有有效记录。

## 5. 用户与典型场景

### 5.1 目标用户

首期唯一目标用户为项目研发者本人。

### 5.2 典型研发场景

- 不强依赖特定语言或平台的普通代码开发。
- MCU 程序、设备驱动和 PX4 二次开发。
- Zynq FPGA 与多核 ARM 异构系统开发。
- KiCad、Altium Designer、Cadence 等硬件原理图和 PCB 开发。
- PDF、Word、Excel、网页等资料检索、提炼、生成与转换。
- 用户临时提出的其他定制场景。

所有场景都应保留网页、HTML、PDF 等资料的浏览器检索能力，以及从大量资料中提炼信息结构并按需查找内容的能力。

## 6. 首期目标

首期完成以下基础闭环：

1. 首次填充并可按需增量维护五类资源文档。
2. 建立由用户批准的 TOML 工具白名单。
3. 提供六类场景化 Codex 配置。
4. 使用 PowerShell 自动部署配置中启用但尚未部署的工具。
5. 对已部署工具进行分层自动验证。
6. 在单项部署或验证失败时执行限定范围回滚。
7. 记录部署、验证、失败原因和残留项。
8. 使用 Windows DPAPI 加密保存本地凭据。

## 7. 首期非目标

以下内容不在首期实现范围内：

- 定时或无人值守的资源目录更新。
- Linux 和 macOS 的部署与验证支持。
- 独立的跨平台命令行工具。
- Plugins、MCP、Skills 的 MCP 或 App 管理端。
- 工具管理和事件阅读的可视化界面。
- 从行业事件中自动发现、部署和测试工具。
- 对所有第三方系统级依赖保证完全回滚。
- 为每个资源或工具编写完整真实业务场景测试。

## 8. 系统组成

### 8.1 资源目录层

Codex 负责联网检索、来源核验、语义筛选、工程分析和 Markdown 文档更新。

首期维护以下文件：

- `Resources/plugins_market.md`
- `Resources/github_market.md`
- `Resources/MCP_market.md`
- `Resources/tool_market.md`
- `Resources/event_market.md`

### 8.2 白名单与配置层

系统使用独立 TOML 清单作为自动部署的机器可读事实源。建议文件名为：

- `Resources/tool_whitelist.toml`

白名单记录工具身份、类型、来源、固定版本、完整性信息、许可证、权限、风险、批准状态和部署验证信息。Markdown 市场文档不得直接充当自动部署输入。

场景配置只允许引用白名单中状态为“已批准”的项目。

### 8.3 部署与验证层

PowerShell 提供统一执行入口，负责：

- 读取场景配置与白名单。
- 执行环境和依赖预检查。
- 生成变更计划与风险摘要。
- 安装、配置并固定工具版本。
- 执行分层验证。
- 在失败时回滚受管变更。
- 更新验证记录。

具体安装方式应通过类型适配逻辑与核心流程隔离，避免核心流程依赖某个具体 Plugin、MCP 或 Skill。

### 8.4 状态与记录层

系统维护以下状态和记录：

- `Notes/verify_record.md`：工具部署与验证历史。
- `state/README.md`：项目概况、关键边界和使用说明。
- `state/TODO.md`：任务拆解、完成进度和下一步计划。
- `state/LOG.md`：关键排障过程、已知风险和应避免的操作。

## 9. 资源目录需求

### 9.1 通用要求

五类市场文档均使用简体中文和 Markdown 格式，并至少包含：

- 最后更新时间。
- 数据源及版本或采集范围。
- 官方来源链接。
- 采集时间。
- 内容状态。
- 对近似或不完整数据的说明。

项目类条目应尽可能包含：

- 项目或工具名称。
- GitHub 链接或唯一标识。
- Star 数量及采集时间。
- 项目属性。
- 部署条件。
- 核心定位与主要功能。
- 适用工作流。
- 输入要求。
- 输出形态。
- 与研发者工作的相关度。
- 成熟度、维护状态和主要风险。

### 9.2 Plugins 市场

`plugins_market.md` 以当前账户、当前工作区可见的 Codex app-server `plugin/list` 完整响应为唯一收录权威。账户、工作区、Codex 版本、marketplace 可用状态和管理员策略都会影响可见记录；文档必须记录本次采集的这些边界，不得把结果表述为其他账户或工作区的全局目录。

最新要求覆盖旧的“排除无关插件”规则：`plugin/list` 返回的所有记录都必须进入完整清单，不按名称、插件 ID、展示名称或研发相关性删除、合并或去重。上游返回的原始重复记录必须保留；记录身份以 marketplace、插件 ID、`remotePluginId` 和版本的组合确定。研发相关性只影响“研发者重点索引”的排序和选择，不影响完整清单的收录范围。

每次更新必须记录采集时间、Codex 版本、marketplace 数量、原始记录数、加载错误和记录身份。`codex plugin list`、本地 marketplace snapshot、缓存、GitHub 仓库和插件官方网站只能补充描述、许可证、部署条件或风险，不能替代或推断完整清单。`plugin/list` 失败、marketplace 加载错误、schema 不兼容或完整性校验失败时，必须保留上一版有效文档，不得用旧仓库、CLI snapshot 或缓存手动补齐后覆盖。

文档需要同时支持人类快速阅读和后续 Codex 根据工作内容选择插件。人类编写的说明、分类和结论使用简体中文；插件名称、标识符、URL、版本和官方原始描述等证据允许保留原语言，不得把翻译内容伪装为原始证据。

### 9.3 GitHub 热门项目市场

`github_market.md` 维护从 2026 年第 1 周开始的 GitHub 往期热门项目，按周倒序分组，并遵守以下规则：

- 仅收录采集时可确认达到 1,000 Star 以上的项目。
- 同一仓库只保留一个主条目，避免跨周重复。
- 排除与研发者工作明显无关的项目。
- 优先使用可验证的历史来源。
- 可验证历史数据不足时，允许综合 GitHub API、第三方历史榜单和仓库记录进行近似回溯。
- 近似回溯结果必须标注来源、推导方式、可信度和数据不完整性。
- 不得把当前 Star 数量描述为历史周榜当时的精确 Star 数量。

### 9.4 MCP 市场

`MCP_market.md` 从 `github_market.md` 中筛选 MCP 项目，并独立记录白名单中的当前受管 MCP 基线。

入选项目必须满足：能够在不修改上游开源源码的情况下部署并用于 Codex。无法验证部署方式、必须修改源码或明显不兼容的项目不入选。

GitHub 派生内容应保留原所属周次及来源信息，并补充 Codex 部署可行性、所需依赖、凭据需求和潜在冲突。当前受管基线必须区分白名单审批、历史验证和当前注册或部署状态，不能从 `approved` 或旧验证记录推导当前可用。

### 9.5 Skills 与其他 AI 工作流工具市场

`tool_market.md` 从 `github_market.md` 中筛选可加速或辅助研发工作的 Skills 和其他 AI 工作流工具，并独立记录白名单中的当前受管 Skill 基线。

该文档排除：

- 已归入 Plugins 或 MCP 的项目。
- 主要用于训练 LLM、开发基础模型或直接建设 AI 模型的项目。
- 与研发者工作明显无关的工具。

GitHub 派生内容应保留原所属周次及来源信息，并与 `MCP_market.md` 避免重复分类。市场候选和处理建议不能直接改变白名单审批状态。

### 9.6 AI 行业事件市场

`event_market.md` 收录 2026 年以来与研发者工作相关的重大 AI 行业事件，重点关注：

- 机器人与具身或自主系统。
- 嵌入式、边缘计算和硬件行业 AI。
- EDA、FPGA、芯片设计与验证。
- ROS、导航和多模态 AI。
- 可能改变工程研发工作流的重要产品和技术。

相同组织或公司的相关事件归入同一组，组内按时间倒序排列。每条事件至少包含：

- 发生时间。
- 组织主体与合作方。
- 官方或高可信来源。
- 客观事件描述。
- 技术剖析。
- 对工程工作流的影响。
- 生态、商业和技术局限。

事实描述与工程分析必须明确区分。

## 10. 白名单需求

### 10.1 审批方式

白名单采用“系统建议、用户批准”方式维护。

Codex 可以根据官方来源、活跃度、许可证、权限、供应链风险和适用性提出新增、升级、停用或移除建议，但只有用户明确批准后才能改变批准状态。

### 10.2 建议字段

每个白名单条目至少应包含：

- 唯一 ID 和显示名称。
- 工具类型：Plugin、MCP 或 Skill。
- 官方仓库或发布来源。
- 固定的 Tag、Commit 或明确版本。
- 包、归档或关键文件哈希。
- 许可证及其识别状态。
- 安装方式和目标目录。
- 所需运行时及外部依赖。
- 网络、文件、进程和账号权限。
- 凭据需求及凭据引用名。
- 已知冲突和互斥工具。
- 风险等级与风险说明。
- 用户批准状态、批准时间和版本。
- 当前部署与验证状态。

### 10.3 版本策略

所有自动部署工具必须固定到明确版本、Tag 或 Commit。市场更新发现新版本时只能提出升级建议，不得自动升级。

升级应视为一次新的审批和部署操作，并重新执行验证。

## 11. 场景配置需求

首期提供以下文件：

- `Resources/config_note.toml`
- `Resources/config_basic.toml`
- `Resources/config_mcu.toml`
- `Resources/config_zynq.toml`
- `Resources/config_hardware.toml`
- `Resources/config_file.toml`

### 11.1 `config_note.toml`

提供全部候选配置项的注释版本，供用户手动选择启用。注释应说明工具用途、适用场景、依赖、冲突和白名单 ID。

### 11.2 `config_basic.toml`

用于普通代码开发，不强绑定特定平台或语言。配置应保持轻量，只启用通用开发、资料检索和必要的上下文能力。

### 11.3 `config_mcu.toml`

用于 MCU、设备驱动、STM32、RP2350 和 PX4 等开发，侧重 C/C++、构建系统、串口或调试资料、芯片文档及嵌入式工作流。

### 11.4 `config_zynq.toml`

用于 FPGA 与多核 ARM 异构开发，侧重 HDL、仿真、综合、时序分析、Linux 或裸机软件、设备树和软硬件协同调试。

### 11.5 `config_hardware.toml`

用于原理图和 PCB 开发，覆盖 KiCad、Altium Designer、Cadence 等工具相关资料、设计检查、器件数据和文档工作流。具体工具按当前任务选择，不默认同时启用全部生态。

### 11.6 `config_file.toml`

用于 PDF、Word、Excel、网页等资料的检索、读取、提炼、生成和转换，并支持输出 PDF、Word 和 Excel 文件。

### 11.7 配置生成规则

- 仅引用已批准白名单条目。
- 遵循最小充分集原则。
- 明确处理功能重复、互斥和优先级。
- 保留浏览器检索和多类型资料处理能力。
- 生成新配置前，检查启用工具的部署与验证状态。
- 对未部署或未验证的工具，先完成部署与验证，再将配置标记为可用。

## 12. 自动部署需求

### 12.1 支持范围

首期仅支持当前 Windows 环境，以 PowerShell 实现。

- Plugins 安装到 Codex 默认插件路径，优先使用 Codex 原生命令。
- MCP 安装到工作区 `MCP` 目录。
- Skills 安装到工作区 `Skills` 目录。

### 12.2 执行流程

部署流程至少包括：

1. 读取配置及白名单。
2. 校验引用项目已获批准且版本明确。
3. 检查系统环境、目标目录、依赖、网络和凭据。
4. 识别工具冲突和安装顺序。
5. 生成安装前快照及变更清单。
6. 执行安装和配置。
7. 执行分层验证。
8. 写入验证记录。
9. 失败时执行回滚并记录残留。

### 12.3 白名单自动部署

状态为已批准、版本与哈希匹配且风险条件未变化的项目可以自动部署。

出现以下任一情况时不得自动部署：

- 来源、版本或哈希与批准信息不一致。
- 请求的权限超出批准范围。
- 许可证状态发生实质变化。
- 出现新的高风险安全信息。
- 与当前已启用工具存在未解决冲突。
- 需要修改上游源码才能运行。

## 13. 自动验证需求

### 13.1 验证层级

验证按以下层级执行：

1. **静态验证**：检查安装文件、目录、版本、依赖和配置。
2. **加载或启动验证**：确认 Codex 可以发现、加载或启动工具。
3. **最小功能调用**：执行一个不产生破坏性副作用的最小调用，验证基本输入输出。

无法完成后续层级时，必须记录已完成的最高验证层级和阻塞原因。只完成静态验证的工具不得声明为完全可用。

### 13.2 验证记录

`Notes/verify_record.md` 至少记录：

- 工具名称、类型和版本。
- 来源和白名单 ID。
- 部署时间和目标位置。
- 执行的验证层级。
- 使用的最小测试及结果摘要。
- 成功、失败或部分验证状态。
- 失败原因和回滚结果。
- 未清理的系统级依赖或其他残留。
- 凭据缺失等外部阻塞。

记录不得包含密钥、Token、Cookie 或其他敏感数据。

## 14. 失败处理与回滚

### 14.1 单项隔离

某个工具部署或验证失败时，应停止该工具的后续操作并执行回滚。与该工具无依赖关系的其他项目可以继续处理。

### 14.2 强制回滚范围

系统必须恢复：

- 本次操作修改的工作区文件。
- 本次操作修改的 Codex 配置。
- 本次操作写入的受管安装目录。
- 本次操作创建的临时文件和可识别进程。

### 14.3 尽力回滚范围

第三方安装器修改的系统级运行时、包管理器缓存、环境变量、驱动或共享依赖只能尽力卸载和恢复。

无法恢复的内容必须记录具体位置、影响和建议处理方式，不得宣称已经完全回滚。

## 15. 凭据与安全需求

### 15.1 存储方式

凭据存放在本地独立密钥文件中，并使用 Windows DPAPI 加密，使其只能由当前 Windows 用户解密。

密钥文件必须：

- 位于明确的本地受管位置。
- 加入 `.gitignore`。
- 不进入备份、归档或验证记录。
- 不在错误信息中输出解密后的值。

### 15.2 使用边界

配置和白名单只保存凭据引用名，不保存凭据明文。

缺少凭据时：

- 不执行需要该凭据的动态验证。
- 将状态记录为凭据缺失导致的部分验证或阻塞。
- 不通过伪造响应或跳过说明来标记验证成功。

### 15.3 供应链安全

部署前必须核对来源、固定版本和可用哈希。下载内容发生不匹配时立即停止，不允许自动接受新内容。

## 16. 核心工作流

### 16.1 按需更新资源目录

1. 用户明确发出更新请求并指定范围。
2. Codex 检索官方来源和必要的高可信辅助来源。
3. 核验链接、版本、时间和关键事实。
4. 按“宽进严标”原则筛选候选内容。
5. 识别重复、失效和状态变化。
6. 增量更新对应市场文档。
7. 标注数据来源、采集时间、可信度和不完整性。
8. 汇报新增、更新、失效和未能确认的内容。

### 16.2 白名单审批

1. Codex 从资源目录或用户指定来源提出候选工具。
2. 给出功能、版本、许可证、权限、风险和冲突摘要。
3. 用户批准或拒绝。
4. 批准后写入 TOML 白名单并固定版本和完整性信息。
5. 后续变化触发重新评估，不自动继承旧批准。

### 16.3 生成场景配置

1. 明确目标研发场景。
2. 识别所需能力。
3. 优先匹配 Codex 原生能力。
4. 从已批准白名单中选择最小充分工具集。
5. 检查功能重复和冲突。
6. 检查部署与验证状态。
7. 部署并验证缺失工具。
8. 生成或更新场景配置。

### 16.4 部署与验证

1. 预检查和风险确认。
2. 建立安装前快照。
3. 按依赖顺序部署。
4. 逐项执行分层验证。
5. 成功后记录最终状态。
6. 失败时隔离、回滚并记录残留。

## 17. 质量边界

- 不要求将所有需求细化为独立可执行验收条目。
- 事实性信息必须有来源，推断必须明确标识。
- 市场文档首次交付时应包含实际内容，不交付空白模板。
- 更新机制必须可重复执行，但首期由 Codex 按需触发，不建设自动调度。
- 首期只承诺 Windows 环境中的实现与验证。
- 动态验证应使用最小、低风险调用，不执行破坏性真实业务操作。
- 第三方系统级安装无法保证完全回滚，必须透明记录残留。
- 不得通过空壳模块、伪造返回值或跳过失败步骤制造成功状态。
