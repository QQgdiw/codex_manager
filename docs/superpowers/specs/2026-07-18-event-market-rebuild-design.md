# 工程工作流事件市场重建设计

## 1. 背景与目标

现有 `Resources/event_market.md` 已定义工程角色中心的收录边界、来源等级和输出模板，但没有经本轮联网核验的正式事件条目，不能视为已经完成的事件市场。

本次重建覆盖 2026-01-01 至 2026-07-18 已实际发生的重大事件。目标数量约 35 项，但数量不是验收门槛：不得为凑数拆分连续小版本，也不得因筛选过严遗漏能够实质影响用户工作的事件。

文档服务于用户的嵌入式、硬件、机器人、ROS、EDA/FPGA、芯片设计验证、边缘 AI、工程型 Agent/Codex 工作流和工程文档工作，不服务于泛 AI 行业新闻阅读。

## 2. 收录边界

### 2.1 应收录

- 会改变编码 Agent、Codex、Claude Code、GitHub Copilot、Cursor、Gemini CLI 等研发工具能力、接口、权限或配置方式的事件。
- MCP、Plugins、Skills、Agent 配置、子代理、工具调用、安全和供应链生态的重要变化。
- 机器人、具身系统、ROS、导航、多模态感知和自主系统中可影响工程实现的产品、标准或工具链事件。
- 嵌入式、边缘 AI、硬件开发、EDA、FPGA、芯片设计与验证领域的重要工程能力变化。
- 会影响工程资料检索、数据手册、PDF、文档、表格、仓库分析和自动化协作的事件。
- 已公开发生且能通过官方公告、官方文档、官方 changelog、官方仓库 release 或标准组织资料核验的事件。

### 2.2 不收录

- 纯模型训练、微调方法、模型权重、benchmark 排名或只宣称“模型更强”的新闻。
- 融资、组织调整、消费娱乐功能和与用户工程工作没有直接关系的行业新闻。
- 尚未发生的发布预告、路线图承诺、传闻或只有二手来源的内容。
- 无法落到工具选择、工程实现、权限、安全、兼容性或工作流决策的泛趋势。
- 为接近目标数量而拆出的补丁版本、重复公告或无独立工程意义的小版本。

### 2.3 事件粒度

同一产品在短期内连续发布的小版本合并为一个阶段性事件。只有出现独立的权限模型、接口合同、兼容性、安全边界或工程能力变化时，才拆分为不同事件。

同一事实不得因属于多个技术方向而重复收录。每个事件只有一个正式主条目，主题索引可以从多个方向引用该条目。

## 3. 文档结构

采用“组织归档 + 主题索引”结构。

### 3.1 文档头部

记录以下边界：

- 覆盖时间：2026-01-01 至 2026-07-18。
- 更新方式：按需手动触发。
- 收录数量和最后核验日期。
- 官方一手来源要求。
- 事实与工程分析分离规则。

### 3.2 主题索引

主题索引不重复正文，只列事件标题、日期、组织和锚点。索引至少覆盖：

1. 编码 Agent 与工程工作流。
2. MCP、插件、Skills、供应链与安全。
3. 机器人、ROS、导航与自主系统。
4. 嵌入式、边缘 AI 与硬件开发。
5. EDA、FPGA、芯片设计与验证。
6. 工程资料、文档和协作基础设施。

一个事件允许出现在多个主题索引中，但正文只能出现一次。

### 3.3 组织归档

正文按组织分组。同一组织及其合作方的相关事件放在同一组，组内按发生日期倒序排列。组织排序优先考虑事件对用户工作的影响，其次考虑最新事件日期，不按公司规模或媒体热度排序。

### 3.4 正式事件字段

每个事件包含：

- `日期`：事件实际发生或正式发布的日期。
- `组织主体与合作方`：只记录官方来源能够确认的主体。
- `工程领域`：使用稳定的主题标签。
- `官方来源`：至少一个直接链接；多个来源分别说明用途。
- `客观事实`：只写来源能够支持的事实、版本、接口和能力。
- `技术剖析`：解释实现边界、依赖和技术意义，不冒充官方结论。
- `对工程工作流的影响`：明确说明对用户具体工作的价值。
- `局限与风险`：分别覆盖技术、生态、商业、安全或可用性限制。
- `后续关注`：仅记录可执行的观察或验证动作，不自动生成部署授权。

官方名称、标识符、版本和 URL 可保留原语言，其余人类可读内容使用简体中文。

## 4. 候选调研与筛选流程

### 4.1 临时候选总账

调研结果先写入 `.tmp/event-market-audit/` 下的结构化临时记录，不直接写正式 Markdown。每个候选至少记录：

- 唯一候选 ID。
- 日期、组织、标题和主题标签。
- 官方来源 URL 及来源类型。
- 已发生状态。
- 客观事实摘要。
- 对用户工作的具体影响。
- 合并键，用于识别连续小版本或重复公告。
- 保留或排除结论及理由。

临时材料不提交 Git，不包含凭据、Cookie、Token 或认证文件内容。

### 4.2 分领域调研

可并行调研以下互不重叠的领域：

- 编码 Agent、Codex 和开发工作流。
- MCP、扩展生态、安全与供应链。
- 机器人、ROS、导航与自主系统。
- 嵌入式、边缘 AI、硬件、EDA、FPGA 和芯片设计验证。
- 工程资料、文档、仓库和协作基础设施。

子代理只能提交临时候选和来源证据，不得直接修改 `Resources/event_market.md` 或正式状态文件。

### 4.3 主代理复核

主代理逐项完成：

1. 打开官方来源并确认链接可访问。
2. 核对日期、组织、版本、产品名称和关键数字。
3. 确认事件已实际发生，不是预告或路线图。
4. 合并连续小版本和重复公告。
5. 判断能否明确影响用户的工程工作。
6. 区分来源事实、技术分析和工作流判断。
7. 对跨主题事件确定唯一正文归属和多个索引入口。

任何关键事实无法由官方来源确认时，该候选不进入正式文档。

## 5. 价值判定

不设置固定领域配额。候选满足以下任一条件即可具有较高价值：

- 改变用户可用的工程能力、接口或自动化边界。
- 引入需要迁移、兼容、权限、安全或成本决策的变化。
- 为嵌入式、硬件、机器人、ROS、EDA/FPGA 或芯片工作提供新的可执行路径。
- 对工具管理项目的市场、白名单、部署、验证或回滚设计产生直接影响。
- 显著改善工程资料获取、分析、文档生成或协作效率。

“知名”“热门”或“模型能力更强”本身不构成价值证据。预计正式结果约 35 项，允许根据核验结果自然增减。

## 6. 来源和错误边界

- 每个正式事件至少有一个官方一手来源。
- 官方 GitHub release、官方 changelog、官方开发者文档和标准组织公告均属于官方来源。
- 二手报道只能用于发现候选，不能作为正式事件的唯一证据。
- 来源不可访问、日期冲突、事实无法确认或事件尚未发生时，排除候选并保留临时理由。
- 调研或渲染失败时不得覆盖上一版正式文档。
- 不读取、输出或提交 `auth.json`、API key、Token、Cookie 或其他凭据。

## 7. 质量检查

正式文档完成后检查：

- 正式事件数量、唯一事件 ID 和组织分组完整性。
- 每个事件字段齐全，官方来源至少一个。
- 事件日期位于 2026-01-01 至 2026-07-18。
- 组内日期倒序，无重复主条目和未合并的小版本堆叠。
- 主题索引全部指向存在的正文锚点。
- 客观事实、技术剖析、工作流影响和局限明确分离。
- 不包含未来预告、泛 AI 新闻、模型训练内容或真实凭据。
- 人类可读内容使用简体中文。
- `git diff --check` 和项目相关测试通过。

## 8. 状态与交付

正式交付包括：

- 重建后的 `Resources/event_market.md`。
- 调研与核验方法的设计说明和实施计划。
- `state/README.md`、`state/TODO.md`、`state/LOG.md` 的当前状态与证据。
- 独立内容审阅和最终验证记录。

本次工作只完成事件市场，不修改白名单、场景配置、部署状态或验证状态，也不引入新的运行时依赖。
